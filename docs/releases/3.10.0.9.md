# QuickPane 3.10.0.9 (fork)

QuickPane 3.10.0.9 fixes a profile-switch bug introduced in 3.10.0.8, and closes three gaps that kept 3.10.0.8's speed-ups from holding everywhere. An independent review of 3.10.0.8 by a second AI model found all of them, and reproduced the two most serious ones with temporary test folders.

## At a glance

| Change | What you will notice | Tracked in |
|---|---|---|
| Edits stay in the profile you see | Adding, renaming, or reordering right after a profile switch changes the new profile, never the one you left. | [#68](https://github.com/prisant-labs/windows-explorer-quickpane/issues/68) |
| Closed panes let go | A pane section closed while it was about to refresh no longer stays in memory, refreshing, for the rest of the session. | [#69](https://github.com/prisant-labs/windows-explorer-quickpane/issues/69) |
| Startup never waits for the groups folder | A groups folder on a share that does not answer no longer holds up the tray icon at startup. | [#70](https://github.com/prisant-labs/windows-explorer-quickpane/issues/70) |
| Dialog clicks go first | A pin click in an Open or Save dialog navigates before QuickPane writes anything to disk. | [#71](https://github.com/prisant-labs/windows-explorer-quickpane/issues/71) |
| The tab in front, read late | With several Windows 11 tabs, a click goes to the tab in front when the click runs, not the one in front a moment earlier. | [#72](https://github.com/prisant-labs/windows-explorer-quickpane/issues/72) |

## Fixed

**Edits after a profile switch went to the previous profile.** Since 3.10.0.8, QuickPane loads a profile's groups in the background. Until that load finished, the pane went on holding the previous profile's groups, although it already showed the new profile's tab. Adding a tab, renaming, or adding a pin in that moment wrote into the previous profile's folder. Reordering groups could move the previous profile's group folders into the new profile. The moment was short when QuickPane was idle, and longer when other background work was running. Now the pane drops the previous profile's groups at once and shows the new ones when they load. Any edit on a group, tab, or pin outside the current profile's folder is refused and noted in the log.

**Closed pane sections could stay alive.** A section of the pane, such as Groups or Recent, refreshes by queueing a rebuild. When the pane closed after a rebuild was queued but before it ran, the rebuild subscribed the closed section to QuickPane's change notices again. The section then stayed in memory and rebuilt itself after every later change, for the rest of the session. Closing a section is now final, and a closed pane ignores rebuilds that were already queued. This is the most likely explanation found so far for memory growth over a working day, which [#52](https://github.com/prisant-labs/windows-explorer-quickpane/issues/52) still needs to measure.

**A click could go to the tab that was in front a moment earlier.** With several tabs in one Explorer window, QuickPane read which tab was in front before it listed Explorer's windows, and the listing takes two cross-process calls per open tab. QuickPane now reads the tab in front again after the listing. A tab opened during the listing can still be missed in a window that had one tab; the next click finds it.

## Changed

- **Startup.** Loading settings no longer creates the groups folder. That step ran on the thread that shares Explorer's input queue, before the tray icon existed. The background scan of the groups folder already creates it.
- **File dialogs.** A pin click in a dialog's pane hands the navigation to the navigation thread first. QuickPane then records the app for Recent Apps in the background, which means reading the program's version information and rewriting `recentapps.txt`. Saves of that file now take turns, because they can come from two threads.
- **Window event hooks.** QuickPane writes a line to its log when Windows refuses to remove one of its event hooks, or when a hook is removed from a thread other than the one that installed it. Neither happens today.

## Known trade-off

The Recent section's 2-second check compares the Explorer window's title and front tab with the last check, and asks Explorer for the folder only when one of them changed, or every 30 seconds. The title shows only the folder's own name. A move from `C:\Demo\Alpha\Reports` to `C:\Demo\Beta\Reports` therefore changes nothing the check compares, and a visit that ends within 30 seconds is not added to Recent. Windows' own Recent list may still show it. This came with 3.10.0.8's cut in background work, and is recorded in [#74](https://github.com/prisant-labs/windows-explorer-quickpane/issues/74).

## Still open

These came out of the same review and are not in this release:

- [#75 (group edits do disk and shortcut work on the UI thread)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/75): renaming or reordering groups, and pinning from Recent, still read every pin's shortcut on the thread shared with Explorer.
- [#76 (drive icons and drive details load on the UI thread while a pane is built)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/76).
- [#77 (one stalled background task holds up the others)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/77): folder clicks are not affected, because they have their own thread since 3.10.0.8.
- [#78 (cache refills can keep rebuilding sections)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/78), only with more than 600 icons or 4,096 paths on screen.

Also still open from 3.10.0.8: [#51 (every settings change rebuilds every pane)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/51), [#52 (memory over a working day)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/52), and [#53 (the occasional busy cursor)](https://github.com/prisant-labs/windows-explorer-quickpane/issues/53).

## For developers

- `GroupStore.ScanOnce` returns whether it published a complete result. `GroupStore.BelongsTo`, `GroupStore.IsGroupIn`, and `GroupStore.SameRoot` decide which groups, tabs, and pins an edit may touch. Every edit method checks them through `Stale` or `StaleGroup`, and an edit made outside the store checks `IsCurrent`.
- Every pane section's `Detach` is final, and `SidebarControl.BuildSections` detaches the old sections before it clears them.
- `WinEventHub` takes an unhook function that returns the native result.
- The test suite grew from 126 to 156 tests, including a port of the reviewer's two reproductions.
- The "Traps in the code" table in [docs/DEVELOPMENT.md](https://github.com/prisant-labs/windows-explorer-quickpane/blob/main/docs/DEVELOPMENT.md) gained rows for profiles and groups, and for pane lifetime, and records the Recent trade-off.

## Install

Download `QuickPane-3.10.0.9-x64-setup.exe` and run it. It installs for the current user, with no administrator rights. Over an existing QuickPane, including one installed by the original project's installer, it closes QuickPane, replaces the program, and updates the same Add/Remove Programs entry. Your settings, groups, and pins in `%APPDATA%\QuickPane` stay where they are.

The zip holds the same program, for replacing the files by hand instead:

1. Close QuickPane, and wait for it to finish: `Start-Process "$env:LOCALAPPDATA\QuickPane\QuickPane.exe" -ArgumentList '--exit' -Wait`
2. Keep a copy of the current `QuickPane.exe` in `%LOCALAPPDATA%\QuickPane`, so you can go back.
3. Unzip the download, and copy `QuickPane.exe` and `QuickPane.exe.config` into `%LOCALAPPDATA%\QuickPane`, replacing the files there.
4. Start `%LOCALAPPDATA%\QuickPane\QuickPane.exe` again.

`SHA256SUMS.txt` lists the SHA-256 hash of the installer, the zip, and each file inside the zip. The files are not code-signed, so Windows SmartScreen may warn before the installer first runs. This release also carries a GitHub build provenance attestation, which `gh attestation verify <file> -R prisant-labs/windows-explorer-quickpane` checks.
